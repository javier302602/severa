Cambios en SDS de SEVERA

- En general se debe adjuntar el análisis completo de todos los requisitos en todas las secciones donde se hablen o analicen estos requisitos.

- En la sección 1. Introducción, se deben aplicar modificaciones para que se ajuste a las nuevas implementaciones.
- En la sección 1.1. Planteamiento del Problema, se debe modificar para no solo hablar de los problemas de seguridad o vulnerabilidades sino también de otros ámbitos donde se podría aplicar el programa, ahora que ya no esta ligado solo al NVD o al CVSS Score.
- En la sección 1.2. Objetivos y 1.3. Justificación, también aplicar las modificaciones para que el sistema no este ligado solo al NVD.

- En la sección 2.1. Elicitación de Requisitos, se podrían realizar modificaciones a las necesidades y las técnicas de elicitación, debido a que ahora el enfoque del sistema cambia de solo aceptar datos del NVD a aceptar cualquier conjunto de datos.
- En la sección 2.2. Verificación de Requisitos se podría incluir una columna de justificación o aspecto a modificar para lograr cumplir los requisitos de verificación.
- En la sección 2.3. Validación de Requisitos adjuntar el análisis realizado ya que solo se incluye el procedimiento llevado a cabo, más no los resultados.
- En la sección 2.4. Refinamiento de Requisitos, de igual forma, incluir el análisis completo realizada a todos los requisitos.

- En la sección 3.1 Perspectiva del Producto, modificar las funciones del sistema para que se ajuste a las nuevas implementaciones, por ejemplo los datasets que ingresan al sistema ya no deben estar sujetos a la estructura del 
  CVSS Score.
- En la sección 3.3. Suposiciones y Restricciones, modificar las Suposiciones para que se ajuste a las nuevas implementaciones. En las Restricciones aplicar lo mismo.
- Se podría eliminar la sección 3.4 Arquitectura General del Sistema, o bien se lo puede poner como "Restricción Técnica", pero lo mas recomendable seria eliminar esta sección y mover el contenido a un "Documento de Arquitectura".
- En la sección 3.5. Comparación con Plataformas Existentes (Benchmarking), se podría optar por analizar otras plataformas, debido al cambio de enfoque del sistema.

- En la sección 4. Escenarios del Sistema, relacionar cada escenario con su respectivo caso de uso.


- En la sección 5. Sprint Por Modulo para la Gestión del Proyecto, se debería de eliminar, ya que no corresponde a este documento de especificación de requisitos, mas bien esto parece parte de otro documento de la fase de codificación o gestión de requisitos. 
  Se debería investigar mas esta parte para evitar eliminarlo adrede.
